# Free-tier deployment runbook

Deployment is partial: the frontend is on Vercel Hobby, the backend is live on Render Free, and Flyway initialized Neon PostgreSQL on 2026-10-04. The production admin login and draft workflow were verified on 2026-10-05. The Sepolia contract was deployed, source-verified, and exercised with a synthetic issue/revoke on 2026-10-05. On 2026-10-06 a hosted demo certificate was issued through the portal and independently verified as valid against Sepolia. SMTP delivery and the hosted revoke flow remain untested. Use only free plans and leave billing and paid upgrades disabled. Public URLs, contract addresses, transaction hashes, and smoke-test results must be recorded only after they exist. Do not paste passwords, API keys, private keys, or a database URL containing credentials into a chat, issue, commit, or frontend variable.

## Selected services

- **Neon Free:** managed PostgreSQL and a **private** S3-compatible object-storage bucket. Use the same production branch for the database and bucket. The current account billing page shows Free Plan at $0/month, with 1 GB of database storage per project; object storage is included up to 5 GB per project. [Neon current Free plan](https://neon.com/blog/neon-free-plan-1-gb-per-project), [object storage](https://neon.com/blog/neon-backend-is-ga)
- **Render Free:** Docker web service for the Spring Boot API, created from [`render.yaml`](../../render.yaml). Its disk is ephemeral and its service can sleep after inactivity; private PDFs therefore belong in Neon Object Storage. Free Render PostgreSQL expires after 30 days, so it is deliberately not used. Render Free blocks SMTP ports 25, 465, and 587. [Render free limits](https://render.com/docs/free)
- **Vercel Hobby:** Next.js frontend with a free `vercel.app` domain. Hobby is intended for personal, noncommercial use. [Vercel Hobby](https://vercel.com/docs/plans/hobby)
- **Brevo Free:** transactional SMTP (current free quota: 300 emails/day) over port 2525 with STARTTLS, a verified sender, and credentials stored only in Render. Port 2525 avoids Render Free's SMTP port block. [Brevo free limit](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan), [port guidance](https://help.brevo.com/hc/en-us/articles/10905415650322-Which-SMTP-port-should-I-use-Port-587-465-or-2525)
- **PublicNode and OpenFaucet:** use the free public Sepolia RPC `https://ethereum-sepolia-rpc.publicnode.com` for the small demo; it returned chain ID `11155111` on 2026-10-05. Use [OpenFaucet's Sepolia proof-of-work faucet](https://openfaucet.org/ethereum-sepolia) to obtain free test ETH without an account, credit card, or mainnet ETH. Its browser computation can be stopped at any time. Public RPC availability and faucet funds are not guaranteed. The deployment wallet and separate backend issuer wallet both need enough **test** ETH for their transactions. Never purchase mainnet ETH for this assignment. [Public RPC directory](https://github.com/ethereum-lists/chains/blob/master/_data/chains/eip155-11155111.json), [faucet explanation](https://openfaucet.org/about)

Free quotas, account eligibility, and anti-abuse policies can change. Do not add a payment method if the requirement is zero possible charges. On 2026-10-05, Render's Billing page showed Hobby, **No card on file**, $0.00 current and projected charges; Neon showed Free Plan, $0/month; Vercel showed Hobby. On Render, reaching some limits without a payment method suspends free services instead of billing; high outbound traffic to Neon/RPC/storage can also suspend the API. Expect cold starts and no production uptime guarantee. Keep demo traffic and PDF sizes small. Do not enable a paid plan or add a card to get past a quota.

## Deployment order

1. Create the Neon project on Free. Choose a region supported by its Object Storage. Create a private bucket; keep its generated S3 endpoint, region, bucket name, access key ID, secret access key, PostgreSQL host/database/user/password in a secret manager. Convert the PostgreSQL connection details into separate `DATABASE_URL=jdbc:postgresql://<host>/<database>?sslmode=require`, `DATABASE_USERNAME`, and `DATABASE_PASSWORD` values. Do not paste the password-bearing `postgresql://` URL into `DATABASE_URL`.
2. Create two separate Sepolia wallets under user control: an admin for role management and an issuer for the backend. Back up their recovery material offline. Obtain test ETH from a free faucet for deployment and issue/revoke gas. Set `SEPOLIA_RPC_URL` and `SEPOLIA_DEPLOYER_PRIVATE_KEY` in a private deployment shell and put **only** their public addresses in ignored `blockchain/ignition/parameters.json`. From `blockchain`, run `npm ci`, `npm run typecheck`, `npm test`, and `npm run coverage`, then deploy using the existing Ignition command in [`blockchain/README.md`](../../blockchain/README.md). Verify chain ID, constructor admin/issuer roles, code, deployment transaction, and source on the Sepolia explorer before enabling the API gateway. Never commit Ignition's deployment journal or keys. Keep the admin signer distinct from the issuer signer.
3. Create the Vercel **Hobby** project once from the `frontend` directory to obtain its real `vercel.app` origin. This first build can leave `API_PROXY_ORIGIN` unset; do not use the site yet. Create the Render **Free** Blueprint from this repository and [`render.yaml`](../../render.yaml). It does not auto-deploy on each commit. Supply all prompted Neon, storage, and frontend values in Render's secret settings; use `MAIL_ENABLED=false` and `BLOCKCHAIN_ENABLED=false` until those services pass their own setup. Render generates `JWT_SECRET_BASE64` as 256 random bits. Use `SPRING_PROFILES_ACTIVE=prod`, `AUTH_COOKIE_SECURE=true`, `AUTH_COOKIE_SAME_SITE=Lax`, and blank `AUTH_COOKIE_DOMAIN`. Set `FRONTEND_BASE_URL` and `CORS_ALLOWED_ORIGINS` to the exact Vercel HTTPS origin. Render's generated `onrender.com` URL is the API origin. Flyway V1 and Hibernate validation run at backend startup. Confirm `/actuator/health` before continuing.
4. Update and redeploy Vercel with `NEXT_PUBLIC_API_BASE_URL=/api`, `API_PROXY_ORIGIN=https://<actual-render-origin>`, `API_INTERNAL_BASE_URL=https://<actual-render-origin>/api`, and `NEXT_PUBLIC_APP_URL=https://<actual-vercel-origin>`. `API_PROXY_ORIGIN` is a server/build setting; it must be an HTTPS origin with no path. Next.js proxies browser `/api/*` requests to Render so the HttpOnly JWT and readable CSRF cookie are first-party on the Vercel origin. No JWT, wallet key, SMTP secret, database credential, or RPC key may have a `NEXT_PUBLIC_` prefix. Test login, CSRF, and logout in a real browser before opening issuance.
5. Provision the first real admin **once from a trusted local shell**, against the Neon production database, after reviewing the organization/admin public details. Set `PROVISION_ADMIN_ENABLED=true`, `PROVISION_ORGANIZATION_NAME`, `PROVISION_ORGANIZATION_EMAIL`, `PROVISION_ADMIN_NAME`, `PROVISION_ADMIN_EMAIL`, and a strong `PROVISION_ADMIN_PASSWORD` as environment variables. Also set the three `DATABASE_*` values. From `backend`, run `./mvnw -DskipTests package` and `./mvnw org.codehaus.mojo:exec-maven-plugin:3.6.3:java -Dexec.mainClass=com.certchain.auth.ProvisionAdmin -Dexec.classpathScope=runtime` (PowerShell: `./mvnw.cmd` and quote each `-D...` argument). The command runs Flyway, inserts one org/admin in a transaction, stores only a BCrypt hash, and fails on an existing admin email. Do not put provisioning variables in Render. Clear them from the local process after success. Keep `DEV_BOOTSTRAP_ENABLED=false` on Render.
6. Set Render `BLOCKCHAIN_ENABLED=true`, `BLOCKCHAIN_NETWORK=sepolia`, `BLOCKCHAIN_CHAIN_ID=11155111`, `BLOCKCHAIN_RPC_URL`, `BLOCKCHAIN_CONTRACT_ADDRESS`, `BLOCKCHAIN_ISSUER_PRIVATE_KEY`, `BLOCKCHAIN_DEPLOYMENT_BLOCK`, and an appropriate `BLOCKCHAIN_CONFIRMATIONS` value after recording the verified deployment. Store the key only in Render's secret settings. Confirm the backend starts and validates chain ID and contract address. Never send keys through the frontend or this document.
7. Configure Brevo's verified sender and SMTP credentials in Render: `MAIL_HOST=smtp-relay.brevo.com`, `MAIL_PORT=2525`, `MAIL_AUTH=true`, `MAIL_STARTTLS=true`, `MAIL_STARTTLS_REQUIRED=true`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM`, and finally `MAIL_ENABLED=true`. Send only after the verified sender and attachment smoke test succeed. The backend's mail journal preserves issued status on SMTP failure.

## Verification before sharing URLs

- `/actuator/health` responds successfully and Render logs show Flyway V1 applied plus Hibernate schema validation. There must be no startup fallback to an in-memory database or local artifact storage.
- Inspect browser cookies on the Vercel origin: auth is Secure, HttpOnly, SameSite=Lax, host-only; CSRF is readable by the frontend and unsafe requests require its header. Reject an unauthorized portal request, a missing CSRF token, and a cross-tenant UUID.
- Run the product smoke flow with dedicated synthetic demo data: unknown ID; login and create draft; issue and confirm Sepolia transaction, event, chain, contract, and proof; verify VALID; verify an intentionally expired issued record as EXPIRED; download the PDF and decode its QR; check the Brevo email; revoke with a private reason; verify REVOKED; demonstrate a local stored-data hash mismatch on a disposable record. Do not edit real production certificate data for the tamper demonstration.
- Verify one database export and object-storage recovery procedure before relying on the deployment. A Git commit is not a database backup. Keep exports encrypted and out of the repository.

## Rollback and incident handling

- Disable `BLOCKCHAIN_ENABLED` or `MAIL_ENABLED` in Render to stop new external submissions/sends while investigating; existing confirmed chain state and journals remain authoritative. Do not reset the certificate table to undo on-chain state.
- Redeploy a known-good backend commit only if its code accepts the current Flyway schema. Flyway migrations are forward-only here; back up Neon before schema changes. Roll back frontend via Vercel's previous deployment only after checking API compatibility.
- If a key may have leaked, rotate the JWT/SMTP/RPC credential or transfer on-chain admin/issuer roles as appropriate. Treat an exposed issuer private key as compromised even if removed from Git. Do not paste incident secrets into chat.
